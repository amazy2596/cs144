# CS144 Checkpoint 3: TCP 发送端 (The TCP Sender) 译文

TCP 是一种通过不可靠数据报可靠地传输一对流量受控字节流（双向各一个）的协议。两方参与 TCP连接，彼此互为对端（peer）。每个对端同时扮演着自己发送字节流的“发送端”（sender）和接收输入字节流的“接收端”（receiver）。

本周你将实现 TCP 的“发送端”部分。它负责从 `ByteStream`（由发送端的应用程序创建并写入）中读取数据，并将该流转换为一系列对外的 TCP 段（segments）。在对端，TCP 接收端将这些段（那些成功到达的，并非所有段都能到达）重新转换回原始的字节流，并向发送端发回确认（acknowledgments）和窗口通告（window advertisements）。

---

## 你的 `TCPSender` 将负责以下工作：

* **追踪接收端的窗口**：接收包含 `ackno`（确认号）和 `window_size`（窗口大小）的 `TCPReceiverMessage`。
* **尽可能填满窗口**：通过从 `ByteStream` 中读取数据，创建新的 TCP 段（必要时包含 `SYN` 和 `FIN` 标志）并发送它们。发送端应当持续发送段，直到窗口被填满，或者发送端的 `ByteStream` 中没有更多数据可读。
* **追踪已发送但尚未被接收端确认的段**：我们称这些段为**“未决段” (outstanding segments)**。
* **重传未决段**：如果从发送开始经过了足够长的时间，且这些段仍未被确认，则重新发送它们。

> **为什么要做这个？**
> 基本原则是发送接收端允许我们发送的所有内容（填满窗口），并持续重传，直到接收端确认了每一个段。这被称为“自动重传请求” (ARQ, Automatic Repeat Request)。发送端根据接收端窗口的允许，将字节流分割成段并发送出去。
> 感谢你上周的工作，我们知道只要对端 TCP 接收端对每个带索引标记的字节至少接收到一次（无论顺序如何），它就能够重建字节流。发送端的工作就是确保接收端获得每个字节至少一次。

## 2.1 TCPSender 如何知道段丢失了？

你的 `TCPSender` 将会发送一系列 `TCPSenderMessage`。每个消息都包含来自发送端 `ByteStream` 的一个（可能为空）子字符串，使用序列号（seqno）标记其在流中的位置，并在流的开始处标记 `SYN` 标志，在末尾标记 `FIN` 标志。

除了发送这些段，`TCPSender` 还需要**追踪其未决段**，直到它们占用的序列号已被完全确认。
周期性地，`TCPSender` 的所有者会调用其 `tick` 方法，以指示时间的流逝。`TCPSender` 负责查看其未决 `TCPSenderMessage` 的集合，并判定发送时间最久的那个段是否在没有收到确认（即不是该段占用的所有序列号都被确认）的情况下等待了太长时间。如果是，则需要进行**重传**（重新发送）。

以下是关于“等待了太长时间（outstanding for too long）”的具体规则。你将需要实现这部分逻辑。它有些繁琐，但我们不希望你担心那些故意刁难你的隐藏测试用例。本周我们会提供合理的单元测试，并在完成整个 TCP 实现后的 Lab 4 中提供更完整的集成测试。只要你 100% 通过这些测试并且你的实现是合理的，就没有问题。

> **为什么要做这个？**
> 总体目标是让发送端能够及时发现丢失的段并重新发送。重传前需要等待的时间非常关键：你既不希望发送端等待太久（因为这会延迟数据流向接收端应用的速度），也不希望它重传一个即将被确认的段（如果发送端再多等一会儿的话）——那会浪费互联网宝贵的传输容量。

### 重传逻辑规则

1. **时间的流逝**：每隔几毫秒，你的 `TCPSender` 的 `tick` 方法就会被调用，参数会告知自上次调用以来流逝了多少毫秒。使用这个参数来维护 `TCPSender` 自创建以来的总生命时间。**请不要在代码中调用任何操作系统的“时间”或“时钟”函数**——`tick` 方法是你获知时间流逝的**唯一**途径。这能确保实现是确定性的且易于测试。

2. **初始超时时间**：在 `TCPSender` 构造时，会传入一个参数，指定**重传超时时间 (RTO, Retransmission Timeout)** 的“初始值”。RTO 是在重传一个未决 TCP 段之前需要等待的毫秒数。RTO 的值会随着时间而改变，但其“初始值”保持不变。初始代码已将 RTO 的“初始值”保存在名为 `initial_rto_ms_` 的成员变量中。

3. **重传计时器**：你将实现一个重传计时器（retransmission timer）：一个可以在特定时间启动的闹钟，一旦经过了 RTO 毫秒，闹钟就会响（即“超时/过期”）。需要再次强调，时间流逝的概念完全源自 `tick` 方法的调用，而不是获取当前的系统时间。

4. **启动计时器**：每次发送包含数据（在序列空间中长度非零）的段时（无论是第一次发送还是重传），**如果重传计时器未在运行，就启动它**，使其在 RTO 毫秒后过期（使用 RTO 的当前值）。“过期”意味着在未来某个毫秒数时计时器会耗尽时间。

5. **停止计时器**：当所有未决数据都已被确认时，**关闭（停止）重传计时器**。

6. **当 `tick` 被调用且重传计时器过期时**：
   * (a) **重传最早的**（序列号最小的）且尚未被 TCP 接收端完全确认的段。你需要在内部的数据结构中存储这些未决段，以便能够执行此操作。
   * (b) **如果窗口大小非零**：
     * i. 追踪**连续重传的次数**，并将其自增（因为你刚刚重传了数据）。你的 `TCPConnection` 将利用这个信息来判定连接是否已经彻底绝望（连续重传次数过多）并需要强行中断。
     * ii. **将 RTO 的值翻倍**。这被称为“指数退避” (exponential backoff)——它在糟糕的网络中减缓重传频率，避免进一步阻塞网络。
   * (c) **重置重传计时器**并启动它，使其在 RTO 毫秒后过期（注意要使用可能刚刚翻倍后的新的 RTO 值！）。

7. **当接收端给发送端一个确认新数据的 `ackno` 时**（即该 `ackno` 对应的绝对序列号大于之前接收到的任何 `ackno`）：
   * (a) 将 RTO 设回其“初始值”。
   * (b) 如果发送端仍有任何未决数据，**重新启动重传计时器**，使其在 RTO 毫秒后过期（使用 RTO 的当前值）。
   * (c) 将“连续重传次数”重置为零。

你可以选择在单独的类中实现重传计时器的功能，这取决于你。如果这样做，请直接将它写在已有的 `tcp_sender.hh` 和 `tcp_sender.cc` 文件中。

## 2.2 实现 TCP 发送端

我们已经讨论了 TCP 发送端在宏观上**做些什么**（给定一个输出 `ByteStream`，将其分割成段发送给接收端，如果没能及时被确认就重新发送它们），以及在**什么时候**判定一个未决段丢失需要被重传。

现在来看 `TCPSender` 需要提供的具体接口。有四个关键事件需要处理：

### 1. `void push( const TransmitFunction& transmit );`
`TCPSender` 被要求从输出字节流中**填充窗口**：它从流中读取数据，并发送尽可能多的 `TCPSenderMessage`，**只要还有新字节可读且窗口中还有剩余空间**。它通过对这些消息调用传入的 `transmit()` 函数来发送它们。

你需要确保发送的每个 `TCPSenderMessage` 都完全落在接收端的窗口内。让每个单独的消息尽可能大，但不能超过 `TCPConfig::MAX_PAYLOAD_SIZE` 给定的值。

你可以使用 `TCPSenderMessage::sequence_length()` 方法来计算一个段所占用的序列号总数。请记住，`SYN` 和 `FIN` 标志各占用一个序列号，这意味着它们也**占用窗口中的空间**。

> **如果窗口大小为零该怎么办？**
> 如果接收端通告的窗口大小为 0，`push` 方法应该**假装窗口大小为 1**。
> 发送端可能会因此发送一个单字节的段，虽然这可能会被接收端拒绝（且不被确认），但这会促使接收端发送一个新的确认段，从而向发送端透露出其窗口中是否有新空间被释放。如果没有这个机制，发送端就永远无法得知自己何时被允许重新开始发送。
> **这是你的实现中针对零大小窗口唯一需要做的特殊处理**。`TCPSender` 不应该在后续的逻辑中真正记住一个虚假的窗口大小 1。这个特例仅在 `push` 方法内部有效。
> 另外请注意：即使窗口大小为 1（或 20、或 200），窗口也可能是“满的”。“已满的”窗口与“大小为零”的窗口不是一回事。

### 2. `void receive( const TCPReceiverMessage& msg );`
该方法在收到来自接收端的消息时被调用。该消息传达了窗口的左边界（`ackno`）和右边界（`ackno + window_size`）。
`TCPSender` 应当查看其未决段的集合，并**移除任何已被完全确认的段**（即 `ackno` 大于该段所包含的所有序列号）。

### 3. `void tick( uint64_t ms_since_last_tick, const TransmitFunction& transmit );`
时间流逝事件——自上次调用该方法以来流逝了特定毫秒数。发送端可能需要重传一个未决段；它可以调用 `transmit()` 函数来实现重传。
（提示：请不要在代码中使用系统时钟或 `gettimeofday`；关于时间流逝的唯一参考只来自于 `ms_since_last_tick` 参数。）

### 4. `TCPSenderMessage make_empty_message() const;`
`TCPSender` 应当生成并发送一个长度为零、且序列号（`seqno`）设置正确的空消息。这在对端想要发送 `TCPReceiverMessage`（例如因为它需要确认来自对端发送方的一些内容）并且需要生成一个与之配合的 `TCPSenderMessage` 时非常有用。
*注意：像这样不占用任何序列号的段，不需要被追踪为“未决段”，也永远不需要被重传。*

要完成 Checkpoint 3，请查看 `src/tcp_sender.hh` 中的完整接口，并在 `tcp_sender.hh` 和 `tcp_sender.cc` 文件中实现完整的 `TCPSender` 公共接口。我们预期你会希望添加私有方法和成员变量，甚至可能需要一个辅助类。

## 2.3 常见问题解答与特殊情况 (FAQs and special cases)

* **在 `receive` 方法通知接收端窗口大小之前，`TCPSender` 应当默认假设接收端的窗口大小是多少？**
  * 答案是：**1**。

* **如果一个确认号（ackno）只部分确认了某个未决段该怎么办？我是否应该尝试切掉已经被确认的字节？**
  * TCP 发送端*可以*这样做，但对于本课程而言，无需过度设计。**只有当一个段被完全确认时（即它所占用的所有序列号都严格小于 `ackno`），才将其从未决段集合中移除**。在此之前，将每个段视为完全未确认。

* **如果我发送了三个独立的段分别包含 "a"、"b" 和 "c"，且它们一直没有收到确认。之后我能把它们合并成一个包含 "abc" 的大段重新发送吗？还是必须分别重传每个段？**
  * 同样地，TCP 发送端*可以*选择合并，但对于本课程而言，无需过度设计。**只需分别追踪每个未决段，当重传计时器过期时，重新发送最早的那一个未决段即可。**

* **我应该把空段存入“未决段”数据结构中并在必要时重传吗？**
  * **不要**。只有传输了数据的段（即在序列空间中消耗了长度的段，如包含 `SYN` , `payload` 或 `FIN` 的段）才需要被追踪为未决段并进行重传。一个不占用任何序列号的段不需要被记录或重传。
