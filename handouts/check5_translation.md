## 0 概述 (Overview)

在本周的 Checkpoint 中，你将深入协议栈的下层并实现一个**网络接口（network interface）**：它是穿梭于世界各地的互联网数据报（Internet datagrams）与传输单跳（one hop）的链路层以太网帧（Ethernet frames）之间的桥梁。这个组件可以放置在你之前实验所实现的 TCP/IP 协议栈“下方”，但它也会在不同的环境中使用：当你在 Checkpoint 6 中构建路由器时，它将在不同的网络接口之间路由数据报。图 1 展示了网络接口在两种环境中的适用方式。

在以前的实验中，你编写了一个 TCP 实现，可以与任何其他运行 TCP 的计算机交换 **TCP 段（TCP segments）**。这些段实际上是如何传送到对端的 TCP 实现的？正如我们所讨论的，有几种选择：

*   **TCP-in-UDP-in-IP**：TCP 段可以承载在用户数据报（user datagram，即 UDP）的载荷中。在普通的（用户空间）环境中工作时，这是最容易实现的：Linux 提供了一个接口（“数据报套接字”，`UDPSocket`），允许应用程序仅提供用户数据报的载荷和目标地址，而内核负责构建 UDP 头部、IP 头部和以太网头部，然后将数据包发送到合适的下一跳。内核确保每个套接字都具有本地/远程地址和端口号的独占组合，并且由于内核是写入 UDP 和 IP 头部的实体，因此它可以保证不同应用程序之间的隔离。
*   **TCP-in-IP**：在常见用法中，TCP 段几乎总是直接放在互联网数据报（IP）内部，在 IP 头部和 TCP 头部之间没有 UDP 头部。这就是人们所说的“TCP/IP”。这实现起来稍微困难一些。Linux 提供了一个名为 `TUN` 设备的接口，允许应用程序提供整个互联网数据报，而内核负责处理其余部分（编写以太网头部，并实际通过物理以太网卡发送等）。但现在应用程序必须自己构建完整的 IP 头部，而不仅仅是载荷。
*   **TCP-in-IP-in-Ethernet**：在上述方法中，我们仍然依赖 Linux 内核来处理部分网络栈。每次你的代码向 `TUN` 设备写入 IP 数据报时，Linux 必须构建一个以该 IP 数据报为载荷的合适链路层（以太网）帧。这意味着 Linux 必须在已知下一跳 IP 地址的情况下，找出下一跳的以太网目的地址（MAC 地址）。如果它还不知道这个映射，Linux 会广播一个查询，询问：“谁拥有以下 IP 地址？你的以太网地址是什么？”并等待响应。

这些功能都是由**网络接口（network interface）**执行的：该组件负责将出站的 IP 数据报翻译成链路层（例如以太网）帧，反之亦然。（在真实系统中，网络接口通常具有类似 `eth0`、`eth1`、`wlan0` 等名称。）**在本周的实验中，你将实现一个网络接口，并将其粘合在你的 TCP/IP 协议栈的最底部。** 你的代码将生成原始以太网帧，这些帧将通过一个称为 `TAP` 设备的接口移交给 Linux——类似于 `TUN` 设备，但更为底层，因为它交换的是原始的链路层帧，而不是 IP 数据报。

大部分工作在于查找（并缓存）每个下一跳 IP 地址对应的以太网地址。用于此目的的协议称为**地址解析协议（Address Resolution Protocol），即 ARP**。

我们为你提供了单元测试来测试你的网络接口。在 Checkpoint 6 中，你将在 TCP 上下文之外，将相同的网络接口用作 IP 路由器的一部分。

## 2 Checkpoint 5: 地址解析协议 (The Address Resolution Protocol)

你的主要任务是在 `network_interface.cc` 文件中实现 `NetworkInterface` 的三个主要方法，维护从 IP 地址到以太网地址的映射。这个映射是一个缓存（cache），或称为“软状态（soft state）”：网络接口保留它是为了提高效率，但如果它必须从头开始重建，映射会自然重新生成，而不会引起任何问题。

### 1. `void NetworkInterface::send_datagram(InternetDatagram dgram, const Address &next_hop);`

当调用者（例如，你的 `TCPConnection` 或路由器）想要向下一跳发送出站互联网（IP）数据报时，会调用此方法。你的接口的工作是将该数据报翻译成以太网帧并（最终）发送出去。

*   **如果目标以太网地址已已知**：立即发送。创建一个以太网帧（其中 `type = EthernetHeader::TYPE_IPv4`），将载荷设置为序列化后的数据报，并设置源地址和目的地址。
*   **如果目标以太网地址未知**：广播一个针对下一跳 IP 地址的 ARP 请求，并将该 IP 数据报排队，以便在收到 ARP 响应后发送。
    *   **特例**：你不想让 ARP 请求淹没网络。如果网络接口在**过去 5 秒内**已经发送了针对同一 IP 地址的 ARP 请求，**不要发送第二个请求**——只需等待对第一个请求的响应即可。同样，将数据报排队，直到你获知目标以太网地址。

### 2. `void NetworkInterface::recv_frame(const EthernetFrame &frame);`

当以太网帧从网络到达时调用此方法。代码应当忽略任何并非发送给该网络接口的帧（即，以太网目的地址既不是广播地址，也不是接口自身的以太网地址（存储在 `ethernet_address` 成员变量中））。

*   **如果传入的帧是 IPv4 类型**：使用 `helpers.hh` 中的 `parse()` 函数将载荷解析为 `InternetDatagram`。如果成功（即 `parse()` 函数返回 `true`），将得到的数据报推入 `datagrams_received` 队列。
*   **如果传入的帧是 ARP 类型**：将载荷解析为 `ARPMessage`。如果成功，**学习并记录发送方 IP 地址与以太网地址之间的映射，有效期为 30 秒**。（从 ARP 请求和响应中都要学习映射。）此外，如果这是一个**询问我们 IP 地址的 ARP 请求**，发送一个适当的 ARP 响应。

### 3. `void NetworkInterface::tick(const size_t ms_since_last_tick);`

随着时间的流逝而调用此方法。使任何已过期的 IP 到以太网映射失效（清除）。

## 3 问题与解答 (Q & A)

*   **你们预期会有多少代码？**
    总体而言，我们预期在 `network_interface.cc` 中的实现总共需要约 100–150 行代码。
*   **我该如何“发送”一个以太网帧？**
    对其调用 `transmit()` 成员函数。
*   **我应该使用什么数据结构来记录下一跳 IP 地址与以太网地址之间的映射？**
    完全取决于你！
*   **我该如何将 `Address` 对象形式的 IP 地址转换为可以写入 ARP 消息的原始 32 位整数？**
    使用 `Address::ipv4_numeric()` 方法。
*   **如果网络接口发送了 ARP 请求但从未收到回复该怎么办？我应该在超时后重传它吗？还是使用 ICMP 向原始发送方报告错误？**
    在现实生活中，是的，这两件事都需要做。但在此实验中不需要担心这些。（在现实生活中，如果接口无法获得其 ARP 请求的回复，它最终会通过互联网向原始发送方发回一个 ICMP“主机不可达”报文。）
*   **如果一个 IP 数据报正在排队等待获取下一跳的以太网地址，但该信息一直没有到来该怎么办？我应该在一定超时后丢弃该数据报吗？**
    是的，网络接口存储数据报的时间不应超过它愿意为同一个 IP 地址发送另一个 ARP 请求的时间（即 5 秒）。
*   **在这个 PDF 发布后，我可以在哪里阅读更多的常见问题解答（FAQs）？**
    请定期检查网站（https://cs144.github.io/lab_faq.html）和 EdStem。
